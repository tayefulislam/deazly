## 5. Configuration design (proposed)

**`tsconfig.base.json` — shared strict, framework-neutral options:**

- `strict: true`, `noUncheckedIndexedAccess: true`, `noImplicitOverride: true`, `noFallthroughCasesInSwitch: true`, `noUnusedLocals: true`, `noUnusedParameters: true`, `forceConsistentCasingInFileNames: true`, `isolatedModules: true`, `verbatimModuleSyntax: true`, `skipLibCheck: false`.
- `exactOptionalPropertyTypes: true` (decision D5) — enabled: strictest sound default, and no legacy type shapes exist to conflict with it.
- No `module`, `moduleResolution`, `target`, `lib`, `jsx`, `types` or emit-target settings in the base; those belong to each app/package so browser and server boundaries stay explicit. `noEmit: true` is centralized in the base because every workspace is typecheck-only.
- TypeScript 6.0 defaults `module` to `esnext` and `target` to the current-year ES version; the base restates the strictness options explicitly and each app/package sets its own `module`/`target`/`lib`, so policy does not depend on compiler defaults.

**App configs (differ by application type, per ADR-003):**

- Next.js frontends (`storefront`, `vendor`, `admin`, `warehouse`): browser-oriented — `lib: ["DOM", "ES2023"]`, `jsx: "preserve"`, `module: "ESNext"` with `moduleResolution: "Bundler"`, `allowJs: false`. TypeScript 6 treats `dom.iterable`/`dom.asynciterable` as empty, so those entries are intentionally omitted. `noEmit: true` is inherited from the base (Next.js owns emission).
- `apps/api` (NestJS): server-oriented — `lib: ["ESNext"]`, `target`/`module`/`moduleResolution` set to Node semantics, `noEmit: true` (NestJS/`tsc` build happens in M1-T23), decorator support enabled for later NestJS use (a TypeScript option, not a framework dependency).
- `apps/worker` (Node): same server-oriented family as `api`, with no browser and no public HTTP typing.
- Never expose browser apps to server-only libs, and never place server packages on the browser libs.

**Shared package configs (`database`, `ui`, `contracts`, `validation`, `config`):**

- Extend the base with `noEmit: true`; `composite: true` and project references are **excluded** (decision D4).
- `packages/database` and `packages/config` remain server-only; `packages/ui` remains browser/presentation-only; `packages/contracts` and `packages/validation` remain framework-neutral. The alias map must not create a `contracts`↔`validation` cycle (ADR-005 §14) and must not expose private/undeclared entry points.

**Path aliases (proposed; boundary-safe):**

- `@deazly/database`, `@deazly/ui`, `@deazly/contracts`, `@deazly/validation`, `@deazly/config` → the corresponding package public entry point only.
- No alias may point into another package's private subpath. Apps may import shared packages; shared packages may not import apps (ADR-005 backend↔frontend and ownership rules). Alias enforcement itself is M1-T03.

## 6. TypeScript version pinning — decided (D2)

M1-T02 introduces the **first** third-party dependency. It is an exact pin, mirroring the Node/pnpm pin discipline.

- Official source: [microsoft/TypeScript releases](https://github.com/microsoft/TypeScript/releases) and the npm `typescript` package.
- Availability/compatibility verified 2026-10-19: `typescript@6.0.3` is published and reports `engines.node: ">=14.17"` — compatible with the pinned Node 24.22.0. (Registry confirmation only; not a build test.)
- **Decided pin (D2): `typescript@6.0.3`** — the Project Owner directed "prefer 6.0.3 if its availability and compatibility are confirmed," and both are confirmed. Recorded as an exact root `devDependencies` entry (no caret/range) and asserted by the config test.
- TypeScript 6.0 config notes: `module` defaults to `esnext`, `target` to the current-year ES version, `dom.iterable`/`dom.asynciterable` are now empty, and `moduleResolution: node`/`node10` and `baseUrl` are deprecated/removed. The configs avoid `node10`, `baseUrl` and a bare `node` resolution.
- TypeScript 7.0.2 exists but is **not** selected for M1-T02; it drops several TS 6.x deprecated options and changes compiler defaults.
- No other dependency is added by M1-T02 (no `@types/node`, no `react`, no `next`, no `@nestjs/*`). Where strictly-typed `lib`/`types` would need such packages, those are deferred to the tasks that write that code (M1-T23/M1-T24).
