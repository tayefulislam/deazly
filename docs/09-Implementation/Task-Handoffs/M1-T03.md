## 5. Configuration design

**`eslint.config.mjs` (flat config):**

- Base for all files: `@eslint/js` recommended, `typescript-eslint` recommended (not type-checked to keep lint fast and framework-free), `eslint-config-prettier` last.
- `files`: `**/*.{ts,tsx,mjs,cjs,js}`; ignore `node_modules`, `.pnpm`, `dist`, `build`, `.next`, and the lockfile.
- TypeScript parser options use the root `tsconfig.base.json` plus each file's nearest config via `projectService` disabled; lint is syntax/scope-based, not type-aware (types are enforced by `pnpm run typecheck`).
- **Boundary rule groups (ADR-005 §3/§14 mapping):**
  - `apps/**`: ban deep package paths (`@deazly/*/src/**`, `@deazly/*/dist/**`) and relative escapes into other workspaces (`../../packages/*/src/**`, `../../apps/*/src/**`); allow only public `@deazly/*` entry points and own relative imports.
  - Browser workspaces (`apps/storefront`, `apps/vendor`, `apps/admin`, `apps/warehouse`, `packages/ui`): additionally ban `@deazly/database` and `@deazly/config` (server-only).
  - Server workspaces (`apps/api`, `apps/worker`, `packages/database`, `packages/config`): ban `@deazly/ui` (browser-only).
  - `packages/contracts`, `packages/validation`: ban importing any other `@deazly/*` package (framework-neutral) and any app.
  - All workspaces: ban importing an application (`@deazly/storefront|vendor|admin|warehouse|api|worker`).
- Boundary rules use ESLint built-in / `typescript-eslint` `no-restricted-imports` patterns — no additional boundary plugin dependency. In addition, literal dynamic imports (`import("…")` with a string-literal specifier) are enforced with the built-in `no-restricted-syntax` rule, deriving selectors from the same ban groups, so static bans are not bypassed via `import()`.

**`.prettierrc.json`:** `{ "printWidth": 120, "semi": true, "singleQuote": false, "trailingComma": "all" }`.

**`.prettierignore`:** `docs/`, `*.md`, `node_modules/`, `.pnpm/`, `pnpm-lock.yaml`, `.git/`. Markdown/planning docs are excluded so formatting never mass-reformats documentation.

## 14. Enforcement matrix — enforced now versus deferred (ADR-005 §14)

| ADR-005 §14 check | Status | Mechanism / owner |
|---|---|---|
| Static import/export restrictions (deep subpaths, app imports, browser↔server, neutral→runtime, contracts) | **Enforced now** | `@typescript-eslint/no-restricted-imports` path-scoped groups |
| Literal dynamic imports (`import("…")` with string literal) | **Enforced now** | built-in `no-restricted-syntax` `ImportExpression[source.value=…]` selectors derived from the same ban groups |
| Non-literal dynamic imports (computed specifiers) | **Deferred** | Not statically analysable; requires resolved-graph tooling or runtime/architecture tests |
| TypeScript aliases, package exports, barrels, type-import edge cases, full module graph / SCC self-import detection | **Deferred** | Requires a separate resolved-graph checker (new task ID in a future backlog revision; not M1-T25) |
| NestJS DI/provider graph and `forwardRef`/global-lookup cycles | **Deferred** | Requires API skeleton (M1-T23) plus runtime or architecture tests |
| Cross-owner SQL / migration ownership checks | **Out of M1-T03 scope** | ADR-005 §14 raw-SQL containment; future ORM/migration task (M1-T05) |

M1-T03 therefore does **not** claim full ADR-005 enforcement. The deferred checks have no existing task ID; they must be added under new IDs in a future backlog revision, without renumbering existing IDs, and remain unauthorized until Gate 0 and a specific exception allow them. This matrix is also summarized in [[09-Implementation/Foundation-Development-Gate]] §12.3.
